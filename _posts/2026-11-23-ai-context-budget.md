## 问题与为什么值得读
{: #why}

文章标题是 *Effective context engineering for AI agents*。作者署在文末致谢里：Anthropic 应用人工智能团队的 Prithvi Rajasekaran、Ethan Dixon、Carly Ryan、Jeremy Hadfield；参与的还有 Rafi Ayub、Hannah Moran、Cal Rueb、Connor Jennings。页面日期是 2025 年 9 月 29 日。我读的官方页是 <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>。

全文要解决的问题是：用大语言模型做能跑很多轮的代理时，难点已经不只是把提示写漂亮。模型这一次采样能看见的全部记号，叫做上下文。记号，是模型处理文字时的计量单位，一段话会切成很多个。上下文工程，是他们给这件事起的名字：在推理的时候，挑选并维持那一组最有用的记号，包括提示以外掉进来的工具结果、外部数据和对话历史。

这篇值得读，是因为它接在他们自己早先那篇代理文章后面，把「模型在循环里自己用工具」这件事的成本说具体了。循环每走一轮，都可能产生下一轮用得上的新材料。窗口装不下全部。他们的判断是：要的是最小的一组高信号记号，使想要的结果更可能出现。这不是一篇发布公告。

用户没有提供全文。下面按我打开的这一页，依原文顺序做详细转述，加上少量短摘译。不是逐段完整翻译。后文里「他们」指这篇文章的作者团队。

## 按原文顺序拆解
{: #reading}

### 提示工程还在，但管不住整窗

原文把上下文工程看成提示工程的下一步。提示工程，是把给模型的指示写好、排好，尤其是系统提示。系统提示，是每次对话开始时就放进去的那份固定说明。他们说，早年多数正式用途是一次就做完的分类或生成，提示是工作的大头。

代理会连续推理很多轮，时间也拉长。这时要管的是整个上下文状态：系统指示、工具、模型上下文协议（Model Context Protocol，一种把外部工具接给模型的统一接法）、外部数据、消息历史，以及其他会落进窗口的东西。

他们的原话方向是：代理在循环里不断造出可能与下一轮有关的数据，这些数据必须一轮一轮地筛选。上下文工程是从不断变大的可能信息里，挑出要放进有限窗口的那一部分。写提示是一次写完的事。上下文工程是反复的：每次决定把什么交给模型，都要再挑一次。

这是原文的划分。我的理解：提示是窗口里的一种材料。材料从哪来、留下哪几条、什么时候丢掉，是另一件工作。把第二件工作仍叫「把提示改好」，会漏掉工具结果和历史。

### 窗口变大，注意力会被摊薄

他们观察到，模型处理更大量数据时，到了某个程度会像人一样失焦或混乱。他们把针在草堆里那种基准测试里露出的现象叫做上下文腐烂：窗口里的记号变多，模型从这份上下文里准确回忆信息的能力就下降。有的模型掉得缓一些。他们说这个特点在所有模型上都会出现。

因此上下文是一份有限资源，多加记号的好处会递减。他们用了一个类比：人的工作记忆有限，模型也有一份「注意力预算」。每新加一个记号，都花掉预算的一部分。这是他们的类比，不是一项我能在这里复述的人体实验。

预算为什么紧，他们归到结构上。Transformer 这种结构让每个记号都能注意到其他每一个记号，n 个记号就有 n 的平方那么多对关系。上下文变长，这些关系被拉薄。训练数据里短序列通常比长序列多，模型对跨全文的依赖见得少，专门的参数也少。位置编码插值可以让模型处理比当初训练更长的序列，但他们对记号位置的把握会差一些。这些因素造成的是一条性能坡度，不是一道悬崖：长上下文里模型仍然很能干，但取回信息和做远距离推理时，精度可能低于短上下文。

限制是他们写明的：把窗口做大，不能取消挑选。他们由此说，要做出能干的代理，就得认真做上下文工程。针在草堆里的那些研究，正文没有列出论文名。我不会补标题，也没有重跑那些基准。

### 有效上下文长什么样

原则他们写成一句：找到尽可能小、信号又高的那一组记号，使某个想要的结果更可能发生。做到很难。后面分部件讲这句原则。

系统提示要用清楚、简单、直接的话，并且把说法放在合适的高度。高度有两种常见的失败。一头是把复杂、易碎的逻辑用死规则写进提示，逼出某一种代理行为。这样脆，以后也难维护。另一头是指引又高又虚，给不出具体信号，或者假装双方已经共享了背景。合适的高度要具体到能引导行为，又留出余地，让模型用得上有力的经验规则。他们把这叫做金发姑娘区间，是他们的类比。

做法上，他们建议把提示分成清楚的段，例如背景、工具指引、输出说明，用 XML 标签或 Markdown 标题隔开。同时他们说，模型更强以后，具体用哪一种格式可能没那么要紧。不论怎么分，目标仍是那一组最小、却足够写明期望行为的信息。他们特别加了一句：最小不一定是短。开头仍要给够，代理才会守住你要的行为。最好先用手头最强的模型试一份最小提示，再按试出来的失败，补明确的指示和例子。

工具让代理跟环境打交道，并在工作中拉进新上下文。工具是代理和它的信息、动作之间的合同，所以要省：返回的信息在记号上要省，也要促使代理少做无用动作。他们指向自己另一篇谈怎样写工具的文章，这里不把那篇展开。要点是工具要自成一块、扛得住错误、用途极清楚，参数描述不含糊，并且顺着模型本来就强的地方来。

他们见到的常见失败，是工具集肿大：一个工具包太宽，或者让人无法判断该用哪一个。原文的标准是：一个人类工程师若不能确定此刻该用哪个工具，就不能指望代理做得更好。把工具收成最小可用的一套，也让长对话里的上下文更好修剪。这是他们的工程判断。

例子，也就是少样本提示，他们仍然强烈建议。但他们不建议把每一种边缘情况都塞进提示，想靠清单说完所有规则。要的是一组多样、又有代表性的例子，把期望行为演出来。他们用了一个比喻：对模型来说，例子是「一张抵得上很多字的图」。这是比喻，不是说真的要插图。

总的指导，对系统提示、工具、例子、消息历史都一样：有信息，同时收紧。

### 事先检索，和用到时再取

他们先把代理收成一个简单定义：大语言模型在一个循环里自主使用工具。他们说，和客户一起做下来，现场正在收向这个范式。模型更强，代理的自主程度就可以加大：更能自己走过细微的问题，也能从错误里恢复。这是他们对自己客户工作的陈述。

上下文怎么设计，他们看到一个移动。今天很多人工智能原生应用，仍在推理之前用嵌入向量把相关材料检索出来。嵌入，是把一段文字变成一串数，用来找相近的材料。他们说，做法变得更像代理以后，团队在这种事先检索之外，加上「用到时再取」。

用到时再取，是手里只留轻的标识：文件路径、存好的查询、网页链接。真正的内容到运行时再用工具装进上下文。他们举自己的编程代理 Claude Code：模型可以写有针对性的查询，把结果存下来，用 head、tail 这类命令看大块数据的头尾，而不把整个数据对象装进窗口。他们把这比作人的做法：人不把整座资料库背下来，而用文件系统、收件箱、书签在需要时去取。这是他们的类比。

标识上的元数据还能帮人判断怎么用。同一个文件名 `test_utils.py`，放在 `tests` 里和放在 `src/core_logic/` 里，意思不一样。目录、命名和时间戳，对人和代理都是信号。让代理自己去找，还能逐步披露：每看一步，都给下一步提供线索。文件大小暗示复杂程度，名字暗示用途，时间可以暂时代表相不相关。工作记忆里只留眼下要的，其余靠记笔记持久化。

交换他们写明了。运行时去找，比取一份事先算好的结果慢。还得有人认真做工具和经验规则，否则代理会误用工具、走进死路，或者找不到关键信息，把上下文浪费掉。

有些场合，最有效的是混合：一部分为了快，事先放进去；其余由代理自己决定要不要再找。分界取决于任务。Claude Code 被他们说成混合的例子：`CLAUDE.md` 会不加挑选地先放进上下文；glob 和 grep 则用来当时导航、当时取文件，从而绕开过期的索引和复杂的语法树。他们还说，内容没那么善变的场合，例如法律或金融，混合策略可能更合适。模型再强，设计会更倾向于让聪明的模型自己行动，人的事先挑选变少。即便如此，他们给团队的建议仍是：做能工作的最简单的那件事。这是建议，不是测量结果。

### 长任务：压缩、笔记、子代理

长程任务，是一串动作的记号数会超过窗口，代理仍要保持连贯、记住上下文、对准目标。他们举的尺度是连续工作几十分钟到几小时，例如大型代码迁移或全面的研究。

等一个更大的窗口，他们不把它当成眼前的办法。他们的判断是：在还想要最强表现的场合，各种大小的窗口仍会遇到上下文污染和「哪些信息还相关」的问题。他们用来直接对付污染的三样是：压缩、结构化笔记、多智能体结构。

压缩，是对话快碰到窗口上限时，把内容做成摘要，用这份摘要打开一个新窗口。它通常是维持长期连贯的第一根杠杆。核心是高保真地把窗口里的东西蒸馏出来，让代理继续时性能少掉一点。

Claude Code 里的做法，是把消息历史交给模型去摘要和压缩最要紧的细节。模型留下架构决定、还没解决的缺陷和实现细节，丢掉重复的工具输出或消息。然后代理带着这份压缩后的上下文，加上最近访问的五个文件，继续做。用户得到连续性，又不用自己盯着窗口。

压缩的难处是留什么、丢什么。压得太狠，会丢掉当时看不出、后来才知道要紧的细节。他们建议在复杂的代理轨迹上仔细调摘要提示：先把召回做到最大，确保相关的都留下，再迭代提高精度，去掉多余的。他们举的一种轻、也比较安全的压缩，是清掉工具调用和结果。一次工具调用已经埋在很早的历史里，代理往往不必再看见那份原始结果。他们说，工具结果清理是最近在 Claude 开发者平台上推出的功能。这是产品陈述。我没有在那个平台上核对开关名称。

结构化笔记，他们也叫代理记忆：代理经常把笔记写到窗口外面的存储里，以后再拉回窗口。开销小，记忆却能留住。像 Claude Code 写待办清单，或你自己的代理维护一份 `NOTES.md`。这样可以在几十次工具调用之间，记住进度、关键上下文和依赖。

他们用 Claude 玩宝可梦做非编程的例子。代理在几千步里保持精确计数，例如记着自己在某条路上训练了多少步、某只宝可梦的等级离目标还差多少。原文举的一句是：过去 1234 步一直在 1 号道路训练，皮卡丘已升 8 级，目标是 10 级。没有人专门规定记忆的格式，它自己画出探索过的区域、记住已解锁的成就，并记下哪种攻击对哪种对手更有效。上下文被重置以后，它读自己的笔记，继续多小时的训练或迷宫。他们说，这种跨摘要的连贯，使长策略成为可能；若把全部信息只放在窗口里，做不到。这是他们对他们自己这个代理的描述。我没有复现这局游戏。

他们还说，随 Sonnet 4.5 发布，Claude 开发者平台上有一个公开测试的记忆工具，用文件系统把信息存在窗口外，供以后查阅。代理可以慢慢积累知识库、跨会话保持项目状态、引用先前的工作。这是当时的产品状态，文中没有给出测试结束的日期。

子代理是绕开上下文限制的另一条路。一个代理不再自己扛整个项目的状态。专门的子代理用干净的窗口做聚焦的任务。主代理拿着高层计划做协调。子代理做深的技术工作，或用工具找信息。每个子代理可以广泛探索，用掉几万个记号甚至更多，但交回来的只是压缩过的摘要，他们写的常见规模是 1000 到 2000 个记号。

效果是分开：详细的搜索上下文留在子代理里，主代理集中综合和分析。他们说，这个模式在另一篇《我们如何建造多智能体研究系统》里讨论过，在复杂研究任务上比单代理有实质改进。改进的幅度写在那一篇，不在这一篇。我这里不补数字。

三样怎么选，他们按任务说：来回很多的任务用压缩，保住对话的流动；有清楚里程碑的反复开发用笔记；复杂研究和分析、并行探索划算时用多智能体。即便模型继续变强，跨很长交互保持连贯，仍会是做更有效代理的核心难题。这是他们的判断。

### 结论里他们没有改口

结论把前面收成一次转移：模型更强以后，难处不只是写出完美提示，而是每一步都认真挑选什么进入有限的注意力预算。不论做的是长任务的压缩、省记号的工具，还是让代理用到时再探索，原则同一句：找到最小的一组高信号记号，使想要的结果更可能发生。

他们补了一句限度：这些技术会随模型变。更聪明的模型需要更少的规定式工程，代理可以更自主。能力加大以后，把上下文当成珍贵、有限的资源，仍是做出可靠代理的中心。前半句是趋势判断。后半句是他们不愿意撤回的约束。

## 对工程实践的意义
{: #practice}

这篇文章对工程实践的意义，是把昨天那篇「先写死路径，再考虑代理」推进了一步：一旦真的用循环，循环的产物会反过来塞满下一次推理。窗口是预算。预算的用法是挑选，不是堆积。三样长任务办法的差别在于大块材料放在哪里：压进一份摘要、写在窗外的笔记，或留在子代理那边只交回短结论。他们自己的限制也要留下来：压得太狠会丢后来才显出的细节；运行时查找比事先检索慢；子代理那「实质改进」的数字不在这一篇里。

下面是我写的一个 ESP32 与 OCPP 例子，用来把「用到时再取」和压缩放到充电桩日志上。它不是原文的例子。我没有在设备上跑过，也没有测量它是否比一次把日志塞进窗口更准。OCPP 是桩和中央系统之间的通信协议。MeterValues 是桩上报计量值的一类报文，一条连接上可以很多。

现场只说：某一把枪每隔几分钟就重新连接。标识只留连接器编号和事务编号，不把几天的 MeterValues 全文放进上下文。需要看时，按编号取一个短时间窗。这是我把他们的「轻标识、用到时再取」搬过来。搬得像不像，要靠以后的评测。

若诊断已经走了很多轮，原始报文开始重复，就走到他们说的压缩：留下还没排除的假设、已经看过的时间窗和未解的报错，丢掉早先的原始帧。他们在 Claude Code 里还留下最近五个文件。桩的日志不是文件树。我不会假装「五个文件」可以直接换成「五条报文」。那是我还没测的推断。

<p class="stop">停在读取。这个例子不写桩的配置，不发重启，不操作接触器，也不把模型的结论写成充电曲线下发。那些是写入和设备操作。上下文收得再小，也不能当成已经获准去动设备。</p>

未验证的部分：我没有比较「按编号取一个时间窗」和「把一天的报文做成一篇摘要」哪一个更能找出重连原因，也没有算记号费用。按他们的标准，在测出差别之前，不应该把这套循环做成默认架构。他们证明过的，是他们自己的编程代理和那局游戏里的笔记。充电桩上会不会同样有效，这一篇没有写。
